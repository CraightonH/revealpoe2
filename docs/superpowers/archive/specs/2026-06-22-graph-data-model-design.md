# Graph Data Model — Design

**Date:** 2026-06-22
**Status:** Approved (design); implementation plan to follow.

## Problem

PoE2 data is densely relational — skill gem → granted skill → recommended supports →
which weapon types those supports apply to; affix → eligible bases; unique → base →
granted skill; everything → tags and glossary keywords. The wiki's stated product value
(CLAUDE.md) *is* surfacing those relationships.

Today each relationship is rediscovered ad-hoc: every cross-reference is a bespoke join
written by reading raw JSON (`_byKey` in `gems.js`, the `mods_by_base` joins in `mods.js`,
`affixBaseTargets`, `grantedSkillNames`, the flattened doc set in `theorycraft.js`). Each
new relationship is new bespoke traversal code, and reverse traversals are hand-coded
separately from forward ones. The data layer also depends on `$POE2DATADIR` at runtime.

## Decision Summary

Introduce a **relationship graph** as the data layer, generated by a deterministic
build-time script, consumed by the existing app which keeps all presentation logic.

Explicitly **rejected:** a graph *database* (Neo4j/Memgraph/etc.). The data is read-only,
single-machine, small (~1k gems, a few thousand mods, hundreds of bases), and regenerated
wholesale from source after each game patch. A runtime query engine adds a service, a query
language, and a sync problem for zero benefit at this scale.

## Architecture

```
poe2data/  ──►  build-graph.js  ──►  graph.json  ──►  app (Express)
(source JSON)   (translation/ETL,    (complete,        loads artifact,
                 deterministic)       resolved data)    owns ALL rendering
```

- **`build-graph.js`** — the translation/ETL layer. Reads `$POE2DATADIR`, resolves every
  relationship and every *fact* the site renders (including stat-id → display strings and
  the 559 per-skill stat-translation files), and emits one `graph.json`.
- **The app** loads `graph.json` at boot and renders from it alone. `$POE2DATADIR` becomes a
  **build-time-only** dependency; the running server no longer needs the sibling data repo.
- **Complete-data, not rendered-HTML.** The artifact holds resolved *data* (facts, strings,
  ranges, relationships). The app keeps all *view* logic — `renderGameText`, keyword
  linkification, rarity borders, card layout, CSS. This is a clean data/presentation split.
- **Staleness guard.** The artifact embeds a hash of `poe2data/_manifest.json`. If the
  resolver is edited without regenerating (or the source changes), boot logs a warning.
  `npm run build:graph`, with `--watch` for the dev loop.
- **Format.** JSON to start — zero new dependencies, parses in well under 100ms at this
  scale, matches the existing loader pattern. SQLite is held in reserve *only* if the
  artifact grows large enough to want lazy/partial loading. Measure before switching.

Why build-time over a runtime in-memory build: reproducibility and diffability (commit the
artifact and `git diff` shows exactly what a game patch changed in the relationship graph),
the expensive resolution runs offline rather than in the request path or at boot, and the
artifact is CI-validatable before it ships.

## Graph-Shape Style Guide

These rules make node/edge modeling mechanical and consistent. They are the durable
contribution of this design — follow them whenever the graph gains new data.

1. **Source-only lineage.** The graph is a *pure function of `$POE2DATADIR`*. Nothing the
   app has already transformed may feed the build — no view-models, no search docs, no
   cached/derived store. The current `src/data/*.js` modules are **reference for the logic**
   (how a relationship was derived), never a data input. Where a resolution function is
   reused, it must take raw source as input; if it only works on app-shaped data, it is
   reimplemented against source. Lineage is always `source → graph`.

2. **Node only if traversed.** Promote a value to its own node when users navigate *to* it
   or *through* it, or it groups entities (gem, skill, base, unique, rollable affix family,
   tag, keyword, item class, passive node). Everything else is a property. Because the graph
   is regenerated by a script, promoting a property to a node later costs nothing — so the
   default is conservative: add nodes when a feature needs to navigate by them, never
   speculatively.

3. **One node per source record.** Identified by its stable source id (the Metadata key),
   **never** by display name. Same-named records (the active skill "Unleash" vs. the support
   gem "Unleash") are distinct nodes — they are genuinely different entities with different
   properties. Display name is a label (a property). URL slugs are a separate *routing*
   concern derived on top, with collision-suffixing (as `gems.js` already does).

4. **One typed edge per source relationship.** The edge type is a fixed function of the
   *source field/join that produced it* — not a per-instance decision. The build script
   holds a mapping table. A new edge type appears only when the source data gains a new
   relationship field. Direction = owner → referent. Stored once, traversed both ways
   (reverse queries walk the same edge backwards; the two directions can never drift).

   | Source field / join | Edge type | Direction |
   |---|---|---|
   | `skill_gems.grants_skills[]` | `grants` | gem → skill |
   | `skill_gems.recommended_supports[]` | `recommends_support` | gem → support gem |
   | `mods_by_base` / `spawn_weights` | `rolls_on` | affix → base |
   | unique name → `uniques.json` base | `has_base` | unique → base |
   | unique "Grants Skill:" text | `grants` | unique → skill |
   | `base_items.tags[]` | `tagged` | entity → tag |
   | stat/skill text → glossary | `references_keyword` | entity → keyword |
   | `base_items` key → item class | `in_class` | base → class |

   (Table is illustrative, not exhaustive — extend it as kinds are added.)

5. **Pairing-facts on the edge.** A fact about a *pair* of nodes (e.g. which affix tiers a
   specific base unlocks) lives on the edge. Facts about one entity live on its node.

6. **Every node has a `kind`** (gem/skill/base/unique/affix/tag/keyword/class/passive).
   Drives search grouping and routing.

7. **Searchable text is declared per node kind.** Each kind lists which properties feed the
   full-text index. Search indexes *text* and is independent of the node/property choice —
   a value being a property (not a node) does not make it unsearchable.

8. **Out of scope, by rule.** HTML rendering, `renderGameText`/linkification, rarity
   borders, card layout, CSS stay in the app. The graph holds data and relationships only.
   Provenance (which source field produced a node/edge) is recorded for diffing/debugging.

### Worked search case (validates the rules)

The source already distinguishes the two affix cases, and the rules above reproduce the
desired full-text-search behavior:

- A **rollable affix** is in `mods.json` and joins to bases via `mods_by_base`. It is
  traversed → a **node** with `rolls_on` edges to every eligible base. A search hit returns
  the affix node, which shows all base types it can roll on.
- A **unique-only line** (an effect that exists only on one unique, never as a rollable mod)
  is not in the rollable tables — it is text on that unique → a **searchable property** on
  the unique node. A search hit returns the single unique node.

## Schema (worked example)

```jsonc
// graph.json
{
  "meta": { "sourceHash": "…", "builtFrom": "2026-06-03 scrape", "schema": 1 },
  "nodes": {
    "Metadata/Items/Gems/SkillGemUnleash": {
      "kind": "gem",
      "name": "Unleash",
      "slug": "unleash-support",          // routing identity, collision-suffixed
      "props": { "color": "b", "gemType": "support", "levelReq": [1, 90] },
      "search": "unleash support …"        // assembled per rule #7
    },
    "Metadata/.../FireballSkill": { "kind": "skill", "name": "Fireball" }
  },
  "edges": [
    { "type": "grants", "from": "…SkillGemFireball", "to": "…FireballSkill" },
    { "type": "recommends_support", "from": "…SkillGemFireball", "to": "…SkillGemUnleash" },
    { "type": "rolls_on", "from": "<affix>", "to": "<base>", "props": { "tiers": [4, 5, 6] } }
  ]
}
```

Traversal is generic: outbound = `edges.filter(e => e.from === id)`, inbound =
`e.to === id`. Both directions come from one stored edge.

## Build Pipeline

The substantive effort is **extracting resolution out of the view modules.** Today
`statText.js`, `mods.js`, and `gems.js` mix *resolving facts* (stat-id → string, mod-tier
assembly, grant matching) with *rendering them*. The build needs the resolution half,
re-expressed as transforms over raw source (per rule #1).

Stages:
1. Load source from `$POE2DATADIR`.
2. Resolve nodes per kind (identity, props, declared search text).
3. Resolve edges from the mapping table (rule #4).
4. Assemble per-node search text.
5. Validate.
6. Serialize to `graph.json` with `meta` (sourceHash, builtFrom, schema version).

**CI validation** (the payoff of a build artifact — catch breakage before ship):
- No dangling edges — every `from`/`to` resolves to an existing node.
- No orphan nodes of kinds that must connect.
- Every node has the required props for its kind.
- Slugs unique.

## Sequencing (no big-bang)

Migrate one node kind at a time so the site is never half-broken:

1. Stand up `build-graph.js` + schema + validator with **one** kind end-to-end: gems plus
   their `grants` / `recommends_support` edges. Point the gem pages and search at the
   artifact. Verify parity against current output.
2. Fold in the rest in turn: bases → affixes → uniques → passives → keywords.
3. Old per-module loaders stay until each kind is migrated, then are deleted.

**Parity check.** Compare the graph's output to the current app's output to confirm the
re-derivation matches the hand-crafted results. This comparison is a **test**, never a build
dependency — the graph's lineage stays `source → graph`.

## Non-Goals

- No graph database / runtime query engine.
- No precomputed rendered HTML in the artifact.
- No speculative node promotion — add nodes when a feature needs to navigate by them.
- No unrelated refactoring of the view layer beyond extracting resolution logic.
